# Traceability matrix — pilot lesson → generalized rule

Maps each concrete lesson learned during the pilot project to the problem it solved, the
generalized rule this skill teaches, and where that rule is documented.

| Lesson from the pilot | Problem it solved | Generalized rule | Documented in |
|---|---|---|---|
| One `CrmClient`-shaped interface, called by every channel | Preventing independently-drifting, channel-specific booking logic | Single shared engine, single source of truth — no channel computes or trusts its own availability | `SKILL.md` §1/§8, `references/architecture-and-decisions.md` |
| Script-level lock re-validating inside the lock before writing | Two concurrent booking attempts for the same slot both succeeding | Every mutation acquires a lock/transaction, re-reads fresh data inside it, and re-validates before writing | `references/booking-and-availability-rules.md`, `references/security-and-idempotency.md` |
| Required idempotency key on appointment creation, returning the original result on a repeat | A network retry creating a duplicate booking | Idempotent mutations: same key + same payload → original result; same key + different payload → explicit conflict | `references/security-and-idempotency.md` |
| Snapshot columns on the appointment record (service name/price/duration, staff name) | Editing a service later silently rewriting historical bookings' price/duration | Snapshot business-fact values at creation time; never recompute them from current data later | `references/crm-data-model.md` |
| Spreadsheet auto-coercion of phone numbers, times, and dates on read/write | Data silently corrupted (wrong type, lost leading zeros, shifted time) with no error raised | Normalize at both the write boundary (force plain-text formatting) and the read boundary (per-column-type normalizer); never assume the written type survives | `references/google-sheets-apps-script.md`, `references/production-lessons.md` |
| Date-serial values with no real timezone identity, reprojected incorrectly through a timezone-aware conversion | Local times shifting by hours, sometimes crossing a date boundary | Extract components with the getters matching how the value was actually stored; never reproject a serial-with-no-timezone through a timezone-aware function as if it were a real instant | `references/google-sheets-apps-script.md`, `references/production-lessons.md` |
| Reusing a signed request's envelope across a network retry, rejected by replay protection | A legitimate retry failing because it looked identical to a replay attack | Build a fresh envelope (new nonce/timestamp/signature) per physical retry attempt, while keeping the same idempotency key and business payload | `references/security-and-idempotency.md`, `references/production-lessons.md` |
| Two independent HMAC implementations disagreeing on non-ASCII input because one runtime's crypto call had no explicit charset | A production signature failure limited to exactly the one action carrying free-text user input | Pass the charset explicitly on every runtime's HMAC call; cover with shared cross-runtime test vectors including non-ASCII text, since a same-runtime sign-then-verify test can't catch this | `references/security-and-idempotency.md`, `references/production-lessons.md` |
| Building one in-memory availability context per request instead of re-reading per candidate slot | Read-only availability queries scaling badly with candidate-slot count for no correctness benefit | Load each table once per request, build one context, reuse it across every slot/staff evaluated — but never apply this to a mutating path, which must always re-read fresh data inside its lock | `references/google-sheets-apps-script.md`, `references/production-lessons.md` |
| A time-off record's absolute-instant mirror columns dropped from the schema declaration while the write code kept populating them | Silent, uncrashing data loss that only careful line-by-line comparison could catch | Treat schema declaration and write-path code as one unit checked together on every change; add an automated parity check where possible | `references/crm-data-model.md`, `references/production-lessons.md` |
| Splitting the scripting-platform test suite into small batches, with an aggregated summary and safe cleanup for interrupted runs | Execution-time limits on the real scripting platform preventing a full test run from completing | Provide a per-batch entry point plus an aggregator; never let a real-deployment test run leave orphaned data behind, regardless of whether it completes | `references/google-sheets-apps-script.md`, `references/testing-and-ci.md` |
| One explicit action-name → handler dispatch table in a single file, instead of each domain file self-registering at top level | A load-order hazard where a domain file's top-level registration call could execute before the table it registers into existed | Central, explicit dispatch table referencing handler functions by name (safe regardless of load order); never build a dispatch table via distributed top-level self-registration on a platform that concatenates files into one global scope | `references/google-sheets-apps-script.md`, `references/production-lessons.md` |
| A clean-checkout/worktree validation catching a TypeScript build relying on a locally-generated file the developer's machine already had | CI failing on a fresh checkout despite passing locally, because the local machine had stale generated artifacts masking the gap | Always validate from a genuinely clean checkout before trusting CI will pass | `references/testing-and-ci.md`, `references/production-lessons.md` |
| Explicit "verified with mocks" vs. "verified against a real deployment" language throughout status reporting | Overstating readiness by conflating a passing mock-based test with real external-service verification | Track and report five distinct verification levels honestly for every integration; never claim a higher one than actually reached | `SKILL.md` §11, `references/deployment-and-operations.md` |
| Explicit `DEMO_DATA_REPLACE_BEFORE_PRODUCTION`-style flags on every placeholder value, and a running "client information required" list | Demo/placeholder data being mistaken for real business data, or quietly presented to a client as authoritative | Never invent a plausible business fact; tag every placeholder explicitly and track what's still pending | `references/discovery-and-client-inputs.md` |
| A single, centralized new-client configuration schema instead of scattered per-file edits when reusing the template for another business | Onboarding a new client requiring broad, error-prone manual edits across many files | Centralize everything that differs between clients into one validated configuration; reuse the engine/CRM client/tests/deploy pipeline unchanged | `references/factory-mode-and-client-onboarding.md` |
